# ADR-0003: 事务与并发控制

| 项目 | 内容 |
| --- | --- |
| 状态 | Accepted |
| 日期 | 2026-10-19（2026-10-21 定稿） |
| 关联需求 | §3.4、§7.3、§7.6、FR-008、FR-017、NFR-004 |

## 背景

库存扣减、状态迁移和幂等记录必须在并发下保持正确。应用层"先查再写"在
并发时必然失效，必须依赖数据库的唯一约束、条件更新或行锁兜底。

M0 阶段本 ADR 只有草案。M1 即将落地 `TransactionManager`、仓储条件更新与
并发测试，若不先固定接口签名、死锁判定与错误映射，实现过程中会反复推翻，
并直接决定 T04（事务管理器）、T09–T11（仓储）、T13–T15（用例）的写法。

## 决策

### 1. 事务边界

所有写事务统一通过 `TransactionManager` 执行，签名固定为：

```go
// Do 在同一个数据库事务内执行 fn；fn 返回错误或 panic 时整体回滚。
// 事务内的唯一合法句柄是传入的 tx，禁止在 fn 内使用连接池上的 *gorm.DB。
type TransactionManager interface {
    Do(ctx context.Context, fn func(ctx context.Context, tx *gorm.DB) error) error
}
```

约束：

- `fn` 内的所有读写必须使用传入的 `tx`；直接使用 `db`（连接池）会跑在事务外，
  在回滚时留下脏数据。
- 只读查询不包事务，除非它需要与随后的写入保持同一快照。
- 不提供包级全局 DB 单例；`*gorm.DB` 由 `main` 构造并显式注入。
- `Do` 的整次尝试（含所有重试）共享调用方传入的 `ctx` 预算。下单、支付、
  取消事务的预算为 **5s**（需求 §7.6），由用例层通过 `context.WithTimeout` 设定，
  `Do` 自己不发明新的超时。
- context 到期时驱动会中断查询并关闭该连接，MySQL 侧事务随之回滚；该连接被
  连接池丢弃重建。因此超时不会留下悬挂事务，但会占用一次连接重建成本。
- **签名中的 `*gorm.DB` 是已知的抽象泄漏**：app 层不 import gorm（由
  `internal/archtest` 检查），但通过事务句柄仍能拿到完整 ORM 对象。保留该签名
  是因为仓储端口需要执行条件更新、读取 `RowsAffected` 并区分驱动错误码；再包一层
  自定义 `Tx` 会把 gorm 的能力抄一遍。代价是"app 不得对 tx 调用 ORM 方法"这条
  纪律只能靠评审维持。重新评估的触发条件写在 `platform/db.TransactionManager`
  的文档注释中（app 出现 `tx.Exec` 等方法、引入第二个数据库、或增加非 gorm 实现）。

### 2. 写入方式：条件更新优先，行锁兜底

关键写操作用条件更新，并把影响行数当作并发结果判据：

```sql
UPDATE inventories
   SET available = available - ?, reserved = reserved + ?, version = version + 1
 WHERE sku_id = ? AND available >= ?
```

- `RowsAffected == 1` 表示本次操作生效；`0` 表示前提已不成立。
- **`0` 不是错误，也不重试。** 它是并发结果，由仓储翻译成领域错误
  （如 `INSUFFICIENT_STOCK`），再由 app 层映射为 `httpx.Code`。
- 条件更新作用于唯一索引等值匹配的行，InnoDB 取记录锁而非间隙锁，因此在
  `REPEATABLE READ` 下不会因为"给不存在的行加间隙锁"而扩大冲突面。
- 需要读后写的场景（例如读取 SKU 价格、状态迁移前读取当前状态做校验）才使用
  `SELECT ... FOR UPDATE`；能用条件更新表达的一律不用行锁。

### 3. 锁顺序

同一事务内对多行加锁时，按 `sku_id` 的**字典序升序**（字节序，不是数值序）
逐行执行，不得依赖请求中的商品顺序。原因：任意两个事务若按相反顺序加锁就会
形成环路死锁；固定全序后，死锁只可能来自跨表交叉，概率大幅下降但仍不为零，
因此仍需第 5 节的重试。

### 4. 隔离级别

使用 MySQL 默认的 `REPEATABLE READ`，不改为 `SERIALIZABLE`，也不依赖
`READ COMMITTED`：

- 事务内的普通 `SELECT` 是快照读，保证同一事务内多次读取价格、库存基线一致；
  写操作与加锁读是当前读，能看到最新已提交版本。
- 不超卖由条件更新保证，而不是由隔离级别保证；换成 `SERIALIZABLE` 只会把
  冲突从"行锁等待"变成"更多锁等待与超时"，不增加正确性。

### 5. 死锁与锁等待重试

判定依据是 MySQL 错误码，使用 `errors.As` 提取 `*mysql.MySQLError`：

| 错误码 | 含义 | 处理 |
| --- | --- | --- |
| 1213 | `ER_LOCK_DEADLOCK`（SQLSTATE 40001） | 整个事务可安全重试 |
| 1205 | `ER_LOCK_WAIT_TIMEOUT` | 整个事务可安全重试 |

- **重试粒度是整个事务，不是单条语句。** InnoDB 在检测到死锁时会回滚整个事务，
  继续执行剩余语句只会得到"事务已回滚"的错误。
- 最多重试 **3 次**（总计最多 4 次尝试），退避 10ms / 20ms / 40ms，每次叠加
  ±20% 抖动，避免同批请求在固定时刻再次撞车。
- 剩余预算不足以完成下一次退避时，立即放弃重试，不睡完再失败。
- **重试耗尽返回 `DEPENDENCY_UNAVAILABLE`（503）并附 `Retry-After`。**
  二选一里选它而不选 `CONFLICT`（409）的理由：409 在本系统中专门表示业务语义
  冲突（库存不足、状态机不允许、幂等键冲突），而死锁耗尽纯粹是瞬时争用，
  同一请求稍后重试通常成功；把它报成 409 会让客户端误以为业务前提不成立而放弃。
  客户端可凭幂等键原样重试，不会产生重复业务效果。
- 非 1213/1205 的数据库错误**不重试**：唯一约束冲突（1062）是业务结论，
  超时是预算结论，二者都不因重试而改变。
- **一个显式例外：** 幂等键 `INSERT` 上出现的 1205/代理超时不走本节的整事务重试，
  而是映射为 `IDEMPOTENCY_IN_PROGRESS`（见 ADR-0006 第 4 节）。此时等待的是
  "另一个请求正在处理同一个键"，重试整事务只会再次排到同一个队尾。
  该例外由 `internal/platform/idempotency` 在 `TransactionManager` 之外单独
  处理，不允许扩散到其他语句。

### 6. 事务内禁止外部 I/O

事务持有行锁期间，禁止调用 Kafka、HTTP、Redis、asynq 或任何可能阻塞在网络上的
操作：外部依赖变慢会把持锁时间放大到秒级，直接引发级联锁等待。

**Outbox 写入属于本地写**：`outbox_events` 与业务表同库同事务，只是插入一行，
不触发任何网络调用。真正的外部发布由 `worker` 的 relay 在事务提交后完成（M3）。

这条规则同样解释了为什么 M1 的下单事务要写 Outbox 而不是直接发 Kafka。

### 7. 幂等与唯一性

幂等与唯一性由数据库唯一约束兜底（`idempotency_records` 的
`(scope, user_id, key)`、`orders.order_id`、`reservations.order_id`、
`payments.order_id`），不依赖应用层先查。幂等的具体语义见
[ADR-0006](0006-idempotency-and-response-snapshot.md)。

## 备选方案

- **应用层加分布式锁（Redis）。** 拒绝：Redis 是派生数据，锁失效或主从切换时会
  静默失去互斥；用不可靠的组件去证明正确性，等于把偶发超卖留给线上。
- **乐观锁 + 冲突后重试整个事务。** 部分采用：`version` 字段保留，用于 SKU 管理
  这类低冲突更新的"丢失更新检测"（版本不匹配返回 409）。但库存扣减以条件更新
  为主——热点 SKU 并发高时，乐观锁会把大量请求变成重试风暴。
- **`SERIALIZABLE` 隔离级别。** 拒绝：不增加正确性，只增加锁等待与超时。
- **重试耗尽返回 409 `CONFLICT`。** 拒绝：混淆业务冲突与瞬时争用，见第 5 节。
- **每条语句单独重试。** 拒绝：事务在死锁时已被回滚，语句级重试没有意义。
- **事务内直接发 Kafka 事件。** 拒绝：违反第 6 节；且可能出现"事件已发、事务回滚"
  的幽灵事件。用 Outbox 消除该窗口。

## 后果

- 正面：正确性由数据库保证，可测试、可解释；并发行为在测试中可复现；
  重试与错误映射有唯一出口，排查时不必逐层猜测。
- 负面：
  - 需要显式 SQL 与锁顺序文档，仓储层不能纯靠 ORM 拼装。
  - 热点 SKU 会串行化，吞吐上界是单行锁的排队速度（M2 再做连接池与慢查询调优）。
  - 重试会让 `Do` 的 `fn` 被执行多次，**因此 `fn` 必须可重入**：不得在闭包外
    累积状态，不得在 `fn` 内产生 DB 之外的副作用。这条约束需要写进
    `TransactionManager` 的文档注释并由评审把关。
- 已知未覆盖：死锁在测试中的复现依赖人为构造相反加锁顺序，不能保证每次必现；
  该风险的处置见 M1 计划 §8。

## 验证方式

- 单元测试（`internal/platform/db`）：
  - `fn` 返回错误 → 回滚；`fn` panic → 回滚且 panic 继续向上传播。
  - 注入 1213 / 1205 → 重试到上限；耗尽后映射为 `DEPENDENCY_UNAVAILABLE`。
  - 注入 1062 与普通错误 → 不重试。
  - 重试次数、退避序列符合本 ADR（用可注入的 clock 或 sleep 函数断言）。
- 集成测试（真实 MySQL）：
  - 两个事务按相反顺序加锁，产生真实 1213，验证自动重试后成功。
  - 并发预占 N 次，成功次数不超过库存，`available` 始终非负。
- 代码评审：检查事务内无 Kafka/HTTP/Redis 调用，检查多行写入按 `sku_id` 排序。
- M2 补充：100 并发基线、慢查询阈值、连接池参数复核（本 ADR 不承载容量结论）。
