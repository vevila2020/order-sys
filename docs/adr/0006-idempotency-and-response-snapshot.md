# ADR-0006: 幂等键与响应快照

## 背景

`POST /api/v1/orders` 是"创建资源"的非幂等操作。客户端在超时、连接中断或进程
重启后无法判断订单是否已创建：不重试可能漏单，盲目重试可能重复下单、重复扣库存。

需求 FR-003 要求：同键同体重复提交最多创建一个订单、一次预占；同键异体返回冲突；
键按用户隔离。需求 §8.4 进一步区分两种重复：已完成返回原结果（200），首次仍在
处理中返回 `IDEMPOTENCY_IN_PROGRESS`（409 + `Retry-After`）。

本 ADR 固定键的格式、指纹算法、记录生命周期与并发同键的处理方式。
ADR-0003 已固定这些记录必须与业务写在同一个事务里；本 ADR 说明如何在那个
约束下仍然区分上面两种重复。

## 决策

### 1. 键格式与作用域

- 请求头：`Idempotency-Key`，**必填**；缺失返回 400 `VALIDATION_FAILED`。
- 长度 8–128 字符；允许字符集 `[A-Za-z0-9._:-]`。超长或非法字符在进入数据库前
  直接拒绝——键会进唯一索引，放任超长值等于开放一个存储放大面。
- 作用域是三元组 `(scope, user_id, key)`，唯一约束 `uk_idempotency` 建在这三列上：
  - `user_id` 取自 JWT `sub`，**不取请求体**，防止用户 A 猜到用户 B 的键后读取
    对方订单。
  - 不同用户使用相同键互不影响。
  - `scope` 一期只有 `order.create`；后续接口复用同一张表，靠 scope 隔离，
    不新建表。

### 2. 请求指纹

- 指纹 = `SHA-256(规范化请求体)`，十六进制小写，64 字符，与 `request_hash CHAR(64)`
  对应。
- 规范化规则：
  1. 把原始请求体解析为通用 JSON 树（`json.Decoder` + `UseNumber`，避免大整数被
     转成 `float64` 后丢精度）。
  2. 对象键按字节序升序重新排列；数组保持原有顺序（数组顺序有语义）。
  3. 以无多余空白的方式重新编码。
- 因此"字段顺序不同、空白不同"得到同一指纹；"`1` 与 `"1"`"、"`1` 与 `1.0`"
  得到不同指纹。
- 指纹对**原始请求体**计算，不对解码后的 DTO 计算。理由：幂等语义承诺的是
  "客户端发来的这次请求"，与我们的 DTO 是否新增了带默认值的字段无关；否则每次
  增加请求字段都会让历史键失效。
- 判定顺序：键非法 → `VALIDATION_FAILED`；记录存在且指纹不同 → `IDEMPOTENCY_CONFLICT`；
  指纹相同才进入重放或处理中分支。

### 3. 记录生命周期（单事务）

幂等记录与业务数据在**同一个数据库事务**内读写（ADR-0003 第 1 节）：

```text
BEGIN
  INSERT INTO idempotency_records
         (scope, user_id, key, request_hash, status, expires_at)
  VALUES ('order.create', :user, :key, :hash, 'IN_PROGRESS', NOW(6) + :ttl)
  -- 1062 冲突 → 读记录 → 按第 4 节分支
  ... 业务写入：库存预占、订单与明细、支付单、Outbox ...
  UPDATE idempotency_records
     SET status = 'COMPLETED', response_snapshot = :snapshot
   WHERE scope = :scope AND user_id = :user AND key = :key
     AND status = 'IN_PROGRESS'
COMMIT
```

- `expires_at = 插入时刻 + idempotency.ttl`（默认 24h）。清理属于 M4 的保留任务，
  M1 只写入该列。
- 事务回滚时 `IN_PROGRESS` 记录一并回滚。**不存在"回滚后留下永远处理中的键"
  这一故障形态**，也不需要补偿删除。这是选择单事务方案的核心收益。
- 原子性在两个方向都成立：有订单 ⇔ 有 `COMPLETED` 记录与快照；不会出现
  "订单已建但客户端永远拿不到结果"，也不会出现"快照指向不存在的订单"。
- `UPDATE` 仍带 `status = 'IN_PROGRESS'` 条件并校验影响行数为 1：若为 0，说明记录
  被并发方改写，属于不该发生的状态，返回 `INTERNAL` 并回滚整个事务（宁可失败，
  不可写出快照与订单不一致的数据）。

### 4. 并发同键：由唯一索引排队，而不是轮询

两个请求持同一 `(scope, user_id, key)` 同时执行时，InnoDB 的行为是确定的：

- 后到者的 `INSERT` 在唯一索引上等待先到事务的隐式锁。
- 先到事务 **提交** → 后到者收到 1062；此时记录已是 `COMPLETED`，直接重放快照。
- 先到事务 **回滚** → 后到者的 `INSERT` 成功，自己完整执行一次用例。
- 先到事务 **迟迟不结束**，后到者的 `context` 预算（下单事务 5s）先耗尽 →
  该 `INSERT` 返回 `context.DeadlineExceeded` / `context.Canceled`。

据此定义三条映射：

| 情形 | 返回 |
| --- | --- |
| 1062，记录为 `COMPLETED`，指纹相同 | 200 + 快照中的 `data`（`request_id` 重新生成） |
| 1062，记录为 `COMPLETED`，指纹不同 | 409 `IDEMPOTENCY_CONFLICT` |
| `INSERT` 因等待超时被中断（ctx 到期或 1205） | 409 `IDEMPOTENCY_IN_PROGRESS` + `Retry-After: 1` |

要点：

- **只有 `INSERT` 这一句**的超时被映射为 `IDEMPOTENCY_IN_PROGRESS`；事务中途其他
  语句超时仍是 504 `TIMEOUT`。原因是"卡在等别人处理同一个键"与"自己的处理超时"
  对客户端含义完全不同，前者重试很快会成功，后者需要排查。
- 这个等待窗口内的锁等待超时（1205）**不交给 ADR-0003 的死锁重试**，直接映射为
  `IDEMPOTENCY_IN_PROGRESS`：重试整事务只会再一次撞上同一个排队，没有收益。
- 后到者不需要空转轮询，也不会读到未提交数据；RR 隔离下看不到未提交行，正是
  唯一索引的等待替我们表达了"处理中"。
- 代价（见"后果"）：同键重复请求会占用一个数据库连接直到先到事务结束。同键并发
  本质是小规模重试风暴，不是常态流量，M1 接受该成本；M2 做并发基线时一并观测。

### 5. 响应快照

- 只存成功响应的 `data` 部分（JSON），不存外层信封：`request_id` 属于单次请求的
  追踪标识，重放必须生成新的，否则日志与链路追踪会把两次请求混为一次。
- 重放一律返回 **200**（首次为 201），符合需求 §8.4。
- 只对成功结果写快照。业务失败（库存不足、状态冲突）**整体回滚**，键被释放，
  客户端可用同一键重试并得到与首次无关的新结果——这正是我们希望的行为：
  失败的请求不该占据一个键。
- 快照体积由响应本身决定（订单 + 明细），M1 不设额外上限；若未来响应膨胀，
  改为存 `order_id` 并在重放时查库（见备选方案）。

### 6. 与 Outbox、事件的关系

幂等记录、订单、预占、支付单、`outbox_events` 全部在同一事务提交，因此
"重放返回的订单"必然对应"事件已落库"。重放路径**不**再次写 Outbox——重放发生在
`INSERT` 冲突后的只读分支，不执行任何业务写入。

## 备选方案

- **Redis 幂等（SETNX + 缓存响应）。** 拒绝：Redis 是派生数据，主从切换或实例
  重启会丢键，届时重复请求会穿透到数据库并再建一单；且无法与 MySQL 事务原子提交，
  必然出现"Redis 记了但数据库回滚"或反之的窗口。M3 可以用 Redis 做**快速判定**
  缓存，但唯一性仍以 MySQL 为准。
- **先提交 `IN_PROGRESS`（独立短事务），再执行业务事务。** 拒绝：这是最常见的
  写法，能更快返回 409，但进程崩溃会在库里留下没有对应订单的 `IN_PROGRESS`
  标记，客户端在 TTL 内（最长 24h）持续收到 409。为消除它需要补偿删除、租约或
  陈旧接管，而这些机制本身又会引入"接管者与原始持有者同时写入"的竞态。
  单事务方案用零故障残留换来一个可接受的等待窗口，权衡更优。
- **只缓存 `order_id`，重放时查库组装响应。** 部分采用：若响应结构后续膨胀，
  这是自然的演进方向；M1 响应规模固定且小，直接存快照可避免重放路径再查库，
  也避免"重放时订单已被后续操作改变，导致两次响应不一致"。
- **把 `Idempotency-Key` 放进请求体。** 拒绝：键不是业务数据，放 header 可以让
  同一份请求体搭配不同键（例如用户主动"再下一单同样的商品"）；放 body 会迫使
  业务 DTO 携带与订单无关的字段。
- **对解码后的 DTO 计算指纹。** 拒绝：DTO 增加字段或改变默认值会让历史键的指纹
  失配，把合法的重试误判为 `IDEMPOTENCY_CONFLICT`。

## 后果

- 正面：重复提交不会产生第二单；崩溃不留孤儿键；重放返回与首次一致的业务数据；
  失败请求不占用键；实现只依赖一张表和唯一索引，可测试、可解释。
- 负面：
  - 同键并发时后到者阻塞，最长到自己的请求预算（5s），期间占一个连接。
  - 指纹对原始字节敏感（大小写、数字写法），客户端必须原样重发请求体；
    文档需要在 API 契约里写明。
  - `IN_PROGRESS` 状态在库中只存在于未提交的事务里，运维无法通过查询观察
    "有多少请求正在处理中"；需要时可借助指标而非表。
- 已知边界：`expires_at` 到期后清理任务（M4）才删除记录。在删除前，同一键的
  合法重试仍会命中快照——这是期望行为，TTL 只是控制存储增长，不改变语义。

## 验证方式

- 单元测试（`internal/platform/idempotency`）：
  - 指纹：键序不同、空白不同 → 相同；`1` / `"1"` / `1.0` → 不同；超长整数不丢精度。
  - 键校验：长度 7 / 129、含非法字符 → 拒绝。
- 集成测试（真实 MySQL，M1-T13/T17）：
  - 同键同体两次 → 一个订单，第二次 200 且 `order_id` 相同、库存只扣一次、
    `reservation` 仅一条、`outbox_events` 不重复。
  - 同键异体 → 409 `IDEMPOTENCY_CONFLICT`。
  - 并发同键（第一个事务被测试代码挂起）→ 其余返回 409 `IDEMPOTENCY_IN_PROGRESS`
    且带 `Retry-After`；解除挂起后重试得到 200 与同一订单。
  - 首次因库存不足失败 → 记录不存在（回滚），同键重试可正常下单。
  - 重放响应的 `request_id` 与首次不同。
- 评审检查：`user_id` 来自 JWT；键与指纹不写入日志原文（只记哈希前缀）。
